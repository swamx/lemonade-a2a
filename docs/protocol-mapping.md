# A2A ↔ Lemonade Protocol Mapping

This document defines the integration boundary. It is intentionally conservative: unsupported A2A semantics must fail clearly rather than being silently approximated.

## Discovery

| A2A concept | Lemonade A2A behavior |
|---|---|
| Agent Card | Generated by adapter configuration and verified backend capabilities |
| Agent URL | Public/base URL of the A2A adapter |
| Skills | Explicitly configured; later auto-discovered where reliable |
| Streaming capability | Advertised only when end-to-end streaming is enabled |

## Message mapping

### A2A → Lemonade

MVP text mapping:

```text
A2A Message
  role=user
  parts=[TextPart(...)]
        │
        ▼
OpenAI-compatible message
  {"role": "user", "content": "..."}
```

Multiple text parts are joined in order. File/Data parts require explicit adapters and are not converted implicitly.

Conversation history should preserve A2A ordering and roles where they can be represented faithfully by the configured Lemonade model API.

### Lemonade → A2A

```text
chat.completion
  choices[0].message.content
        │
        ▼
A2A response message / artifact
```

The final implementation must use official A2A SDK constructors rather than handcrafted wire JSON.

## Task lifecycle

A2A tasks can outlive a single HTTP exchange. Lemonade chat completion is normally request/response. The adapter therefore owns task state while Lemonade owns inference.

Proposed mapping:

```text
A2A submitted
    ↓
working       → Lemonade request active
    ↓
completed     → model output committed as response/artifact

failed        → backend/protocol failure with sanitized error
canceled      → client cancellation propagated to backend where possible
```

Task identifiers must be generated by the A2A layer and must not be derived from prompt content.

## Streaming

```text
Lemonade SSE delta
      ↓
parse OpenAI-compatible delta
      ↓
A2A streaming event
      ↓
A2A client
```

Requirements:

- preserve token/chunk order;
- do not buffer the full completion before forwarding;
- stop backend work when client cancellation can be propagated;
- bound queues to prevent a slow client from exhausting memory;
- emit a terminal task state exactly once.

## Artifacts

Text output can be represented directly as an A2A message or text artifact depending on task semantics. Rich artifacts require explicit mappings.

Future mappings may include:

- generated image → file/artifact;
- transcription → text artifact plus metadata;
- structured JSON → data part/artifact;
- code → text artifact with media-type metadata.

## Errors

Backend HTTP failures, malformed model responses, unsupported A2A parts, timeouts, and cancellations must be mapped to protocol-appropriate failures without leaking local filesystem paths, environment variables, API keys, stack traces, or model-server internals.

## Authentication

A2A authentication and transport security are deployment concerns and must be handled before exposing the adapter beyond loopback/trusted LAN. The Lemonade backend should normally remain bound to localhost when the A2A gateway is the externally reachable boundary.

## Compatibility

The implementation should be validated against the official A2A Inspector/TCK where applicable. Compatibility status must be reported as measured test results, not as a blanket claim.
